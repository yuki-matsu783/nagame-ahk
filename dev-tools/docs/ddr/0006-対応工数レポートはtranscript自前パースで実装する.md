# 0006. 対応工数レポートはtranscript JSONLの自前パースで実装する

## 背景

issue #15「作業にかかったトークンなどの情報をMRのコメントに記載する」への対応にあたり、
Claude Codeがトークン使用量をどこから取得できるか公式ドキュメント（code.claude.com/docs/en/hooks）
で調査した。

- `Stop` / `PostToolUse` 等のhookがstdin経由で受け取るJSONペイロードに、トークン数・コスト情報は
  **含まれない**（`session_id` / `transcript_path` / `cwd` / `tool_name` 等の共通フィールドのみ）。
- `transcript_path` が指すJSONLファイルには各assistantメッセージの `message.usage`
  （`input_tokens` / `output_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens`）と
  `message.model` が含まれることを実transcriptで確認した。ただしこのJSONL形式は
  **Claude Code非公開の内部フォーマットであり、将来のバージョンで変更されうる**旨が公式に
  明記されている。
- `claude -p --output-format json` は `total_cost_usd` を含む構造化出力を返すが、これは
  **新規に起動した非対話的セッションの結果**であり、現在進行中の対話セッションの使用量を
  取得する手段にはならない。

## 決定

**他に確実な取得手段が無いため、`transcript_path` のJSONLを自前でベストエフォートパースする方式を
採用する。** 非公開フォーマットへの依存によるリスクは、以下の設計で吸収する。

1. **失敗を握りつぶす**: パースは1行ごとに`try`/`catch`で行い、壊れた行はスキップする。
   集計処理全体も呼び出し元（`post-push-usage-report.ps1`）側で`try`/`catch`し、失敗しても
   git push自体をブロックしない（記録が0件になるだけ）。
2. **金額（USD）は算出しない**: モデル単価表を自前で保守する必要が生じ、かつ実際の請求額と
   ずれるリスクがあるため、トークン数（input/output/cache write/cache read）のみを報告する
   （issue #15の受け入れ条件「何をコメントするかが明確」は、トークン数という生の数値のみで
   十分満たせると判断した）。
3. **コメント本文に「目安として扱ってください」と明記する**: 非公開フォーマット依存の
   ベストエフォート集計であることを利用者に常に伝える。

### `entry.gitBranch` によるブランチフィルタ

transcript の各assistantメッセージには、実行時にチェックアウトされていたブランチ名が
`gitBranch` フィールドとして記録されていることを実機確認した（全assistantエントリでの
付与率100%を確認済み）。

当初の実装（セッション全体の累計を無条件にそのブランチの使用量として扱う）では、
同一セッション内で複数ブランチを跨いだ場合に他ブランチ分のトークンが混入するバグがあった
（issue #15対応中の実データで、無関係な旧ブランチ分が452,144トークン混入していたことを確認）。
`entry.gitBranch -eq $Branch` でフィルタしてから集計するよう修正し、このバグを解消した。

### `PostToolUse`（git push検知）単体で完結させ、`Stop` hookは使わない

`Stop` は1ターン完了時にしか発火しないため、ターン途中で `git push` が実行されると
（例: ブランチ作成・調査・実装・pushを1ターン内で行う場合の最初のpush）、そのターンで
既に消費したトークンが未記録のまま「記録漏れ」に見える問題があった。

当初は「`Stop`の代わりに別のhookで記録する」のではなく、`post-push-usage-report.ps1`
（`PostToolUse`, git push検知）自身が投稿直前に同じ集計処理（`Sync-UsageState`）を
呼んで状態を最新化してから投稿する方式を採用し、`Stop`は「ターン数のカウント」専用の役割
（`sinceLastPush.turns`を+1するだけ）として残していた。`transcript_path` は`PostToolUse`の
ペイロードにも含まれる共通フィールドであるため、これが可能だった。

しかしその後、**`Stop`を完全に廃止**した。理由は次の2点。

1. `post-push-usage-report.ps1` が投稿直前に呼ぶ `Sync-UsageState` だけで、トークン・ツール実行回数
   の集計は既に完結しており、`Stop`はターン数カウントのためだけに残っていた。
2. その`Stop`依存のターン数カウントは、**トークン集計で修正したのと同じ穴**（そのターンの`Stop`が
   まだ発火していない状態でpushすると過少カウントされる）を抱えたままだった。実際、修正前の
   自動投稿コメントは実データ（トークン数・ツール実行回数）があるにもかかわらず
   「対象ターン数: 0」と表示される不整合が確認された。

そこで、ターン数も**「assistant応答回数」**と読み替えた上で、トークン・ツール実行回数と全く同じ
「transcriptとの差分を`sinceLastPush`へ加算する」方式で`Sync-UsageState`内に統合した
（`entry.gitBranch -eq $Branch` のエントリ件数を、セッションの前回記録値
`sessions[$SessionId].lastAssistantCount` と比較して差分を加算）。厳密な「会話ターン数」とは
ずれうる（1ターン内でtool_use往復により複数のassistantメッセージが生成されるため）が、
`Stop`の発火有無に依存しない一貫した値になる。結果、`Stop` hook（`stop-usage-record.ps1`）と
`.claude/settings.json`の`hooks.Stop`設定は不要になり削除した。共通の集計ロジックは
`.claude/hooks/lib/UsageTracking.ps1` に残り、`post-push-usage-report.ps1` のみから呼ばれる。

## 却下した案

- **`claude -p --output-format json` を別プロセスで呼んで集計する**: 公式にサポートされた
  手段だが、新規の非対話的セッションを起動する形になるため、現在進行中の対話セッションの
  使用量を取得する用途には使えない。
- **SessionEndフックで1セッション1回だけ投稿する**: `SessionEnd` は既定1.5秒の共有予算しか無く
  （設定で最大60秒まで拡張可能）、ネットワーク呼び出し（`gh pr comment`）を含む処理には
  タイムアウトリスクがある。加えて「1セッション1回」では、1つの長時間セッションで複数回push
  した場合の粒度が粗すぎる（ユーザーとの合意事項「git push成功時に前回投稿からの差分を投稿」に
  合わない）ため見送った。
- **推定コスト(USD)の算出**: モデル単価表の保守コストと実請求額とのズレのリスクを理由に見送った
  （上記「決定」参照）。
- **状態ファイルの排他ロック**: 複数のClaude Codeセッションが同一ブランチへ同時に書き込む場合の
  レースコンディション対策として検討したが、単一開発者が同一作業ディレクトリで複数セッションを
  同時実行する運用は想定しにくく、実装コストに見合わないと判断し見送った。既知の制約として
  `dev-tools/docs/spec/issue-mr-workflow.md` に記録するに留める。

## 検討の経緯

ユーザーから当初「フックで記録できる主な情報」として、トークン/コスト・ツール実行・ファイル操作・
プロンプト内容・サブエージェント往復などの案が提示されたが、調査の結果Stopペイロード単体では
取得できないことが判明し、範囲を「モデル別トークン数＋ツール実行回数＋ターン数」に絞ることで
合意した（USD推定コスト・ファイルdiff・プロンプト本文・サブエージェント詳細往復は対象外）。
詳細な比較検討は `worklog/2026-08-16_groovy-zooming-balloon.md`（設計反映時に削除予定）を参照していたが、
削除後は本DDRが唯一の記録となる。

## 追記（issue #28, PR #29レビュー指摘）

外部調査（[Claude Code JSONL logs undercount tokens](https://gille.ai/en/blog/claude-code-jsonl-logs-undercount-tokens/)）
によると、transcript JSONLはストリーミング応答の開始時点で`usage.input_tokens`等に
プレースホルダー値（0または1）を書き込み、応答完了後もその値を実際のトークン数へ更新しない
ケースがあり、結果としてinput側で最大100〜174倍、output側で最大10〜17倍の過小カウントが
観測されたと報告されている（キャッシュ関連フィールドはAPIレスポンス初期段階で確定するため
影響を受けにくいとされる）。

本DDRの「決定」で述べた「非公開フォーマット依存によるリスクの吸収策」（失敗を握りつぶす・
目安として明記する）は、この具体的な過小カウント機序が判明する前から採用していた対策だが、
結果的にこの問題にも同じ形で対応できている（プレースホルダーのまま更新されない値であっても
パース自体は成功するため「失敗の握りつぶし」は効かないが、「目安として扱ってください」という
利用者への明示が実質的な対応になる）。回避策（ステータスバー等、他の情報源を使う）は
transcriptの自前パースという設計方針自体を変えることになるため、本DDRの決定を覆すものではないと
判断し、既知の制約として`dev-tools/docs/spec/issue-mr-workflow.md`の「未決定事項・懸念点」に
記録するに留めた。issue #28で追加した稼働時間（`activeSeconds`）は`.timestamp`の差分のみを
使うため、この過小カウント問題の影響を受けない。
