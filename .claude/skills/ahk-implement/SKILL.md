# nagame-ahk 実装フロー

このスキルは `.claude/skills/issue-mr-flow/SKILL.md`（唯一の実装フロー定義）の全体フローのうち、
「設計ドキュメント作成〜実装」ステップ（AHK機能実装の場合）を実行手順に落とし込んだものです。
issue-mr-flowから呼ばれるサブフローという位置づけであり、単独の最上位エントリーポイントではありません。
コーディングの詳細ルール（命名規則、v2固有の注意点など）は `.claude/rules/ahk-style.md` を参照します。

## 手順

### 1. 設計ドキュメントを作成する

- `docs/spec/機能名.md` を新規作成する。
- 既存の `docs/spec/*.md`（例: `docs/spec/activity-status.md`, `docs/spec/logger.md`）と同じ章立てに揃える:
  - 背景・目的
  - 仕様（動作・UI・ホットキー等）
  - 影響範囲（追加・変更するファイル）
  - 設定項目（`Settings` への追加値）
  - 未決定事項・懸念点

### 2. 人間の承認を得る

- 作成した設計ドキュメントの内容をユーザーに提示する。
- **明示的な承認を得るまでコードの実装には着手しない。**
- 修正依頼があれば設計ドキュメントを更新し、再度確認を取る。

### 3. 方針を計画する

- 着手前にfeatureブランチを作成する（未作成なら。詳細は `.claude/rules/git-workflow.md`）。
- ごく簡単なタスクを除き、AIエージェントのplanモード（比較検討した案・手順のチェックリストをまとめ、人間と合意する）を使ってから実装に入る。承認済みの計画は `plans/` に自動出力されるため、そのままコミットして履歴に残す。このタイミングで `worklog/日付_<planファイル名>.md` を作成する。
- spec の「影響範囲」節だけで方針が自明なごく小さな変更（誤字修正・バグ修正・軽微な設定値変更等）に限り、この手順を省略してよい。
- `HANDOFF.md` は作業の節目ごとに頻繁に更新するが、常に「現在地・次回やること」等の軽量な状態のみを保つ。「試した・成功・失敗（エラー内容）・次の一歩」の詳細は `worklog/日付_<planファイル名>.md` に書き足す（同じブランチで作業する間は消さない）。

### 4. 実装する

- `.claude/rules/ahk-style.md` のコーディングルール（命名規則、v2固有ルール、`#Include` 順序、エラーハンドリング等）に従う。
- 機能のエントリポイントとなるファイルの冒頭に、設計ドキュメントへの参照コメントを入れる。
  ```ahk
  ; 設計: docs/spec/機能名.md
  ; （ファイルの役割を1〜2行で記述する）
  ```
- エラーが起こりうる処理は `try/catch` ＋ `Logger.Error` で囲み、原因究明用に要所へ `Logger.Debug` を仕込む。

### 5. 整合性を維持する

- 実装中に設計と異なる判断をした場合は、設計ドキュメント側も合わせて更新する。
- ソースコード側の参照コメントのパスも、ドキュメントのリネーム等に追従させる。
- 実装が完了したらPR作成前に「設計反映」を行う（詳細は `.claude/skills/issue-mr-flow/SKILL.md`）:
  - `docs/spec/機能名.md` を最終仕様に合わせて上書きし、`docs/README.md` にリンクを追記する。
  - 「後で『なぜこうなってるんだっけ』と聞かれそうな決定」をした場合は `docs/ddr/000N-タイトル.md` に記録し、spec側の該当する未決定事項は削除する。
  - 反映済みの `worklog/日付_<planファイル名>.md` を削除し、`HANDOFF.md` を次のタスクに向けてリセットする。
  - PRを作成し、レビュー・承認を経て（人間が）squash mergeでmainに統合する。
