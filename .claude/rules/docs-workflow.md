# 実装フロー・ドキュメント運用

## 実装フロー（必須）

新機能の追加や既存動作の変更を行う前に、必ず以下の手順を踏む。実装を先に進めてはならない。
この手順は `.claude/skills/ahk-implement/SKILL.md` としてスキル化されている。`/ahk-implement` から呼び出せる。
ブランチ・PR・squash mergeの運用は `.claude/rules/git-workflow.md` を参照。

1. 着手前にfeatureブランチを作成する（詳細は `.claude/rules/git-workflow.md`）。
2. `docs/spec/` ディレクトリに設計ドキュメント（Markdown）を作成する。
   - ファイル名: `docs/spec/機能名.md`
   - 記載内容の目安: 背景・目的 / 仕様（動作・UI・ホットキー等） / 影響範囲（追加・変更するファイル） / 設定項目（`Settings` への追加値） / 未決定事項・懸念点
3. 設計ドキュメントの内容について、人間（ユーザー）のレビュー・承認を得る。
4. **承認が得られるまでコードの実装には着手しない。**
5. ごく簡単なタスクを除き、AIエージェントのplanモード（比較検討した案・実行手順をまとめ、人間の承認を得る）を使って方針に合意してから実装に入る。承認済みの計画は `plans/` に自動出力されるため、そのままコミットして履歴に残す。このタイミングで `worklog/日付_<planファイル名>.md` を作成する（詳細は「ドキュメント運用」節）。spec の「影響範囲」節だけで方針が自明なごく小さな変更（誤字修正・バグ修正・軽微な設定値変更等）に限り省略してよい。
6. 承認後に実装する。実装中の試行錯誤（試した・成功・失敗・次の一歩）は `worklog/日付_<planファイル名>.md` に書き足し、`HANDOFF.md` は現在地・次回やること等の軽量な状態のみを保つ。実装中に設計と異なる判断をした場合は、設計ドキュメントも合わせて更新する。
7. 実装時は、対応するファイルに設計ドキュメントへの参照コメントを記載する（詳細は `.claude/rules/ahk-style.md` の「コメント」節を参照）。
8. 実装が完了したらPR作成前に「reflect」を行う。
   - `docs/spec/機能名.md` は最終仕様に合わせて上書きし、`docs/README.md` にリンクを追記する。
   - 実装中に「後で『なぜこうなってるんだっけ』と聞かれそうな決定」をした場合は `docs/adr/` に記録する。
   - 反映済みの `worklog/日付_<planファイル名>.md` は削除し、`HANDOFF.md` を次のタスクに向けてリセットする。
9. PRを作成し、レビュー・承認を経て（人間が）squash mergeでmainに統合する。

## ドキュメント運用

情報の寿命（ライフサイクル）と「誰のためのドキュメントか」で置き場所を切り分ける。

| ファイル | 対象 | 寿命 | 内容 | 運用 |
|---|---|---|---|---|
| `CLAUDE.md` / `.claude/rules/*.md` | AI専用 | 永続 | 規約・構成・実装フロー | ルート直下・`.claude/rules/`。セッション開始時にAIが自動読込する。 |
| `plans/*.md` | 人間＋AI | 生成時点のスナップショットとして永続 | AIエージェントのplanモードが出力する方針・比較検討した案・承認記録 | タスクごとに自動生成され、人間の承認をもって確定する。手動で使い回したり中身を空にしたりせず、そのままコミットして履歴に残す。 |
| `HANDOFF.md` | 人間＋AI | 短期（常に最新状態のみ。詳細はworklogへ） | 現在地／次回やること／参照するファイル／判断が分かれるポイント／未解決の質問／守るべき条件・触ってはいけない範囲 | Git管理下に置く。作業の節目ごとに頻繁に更新する。詳細な試行錯誤は書かず `worklog/` に逃がす。タスク完了・PR作成時（reflect）に次のタスクへ向けてリセットする。 |
| `worklog/日付_<planファイル名>.md` | AI専用（人間も参照可） | ブランチ単位（PR作成前のreflectで削除） | 「何を試した／うまくいった／ダメだったか」の詳細ログ | planモード完了時に作成し、同じブランチで作業する間は書き足す。PR作成前のreflectでspec/adrへ反映したうえで削除し、削除自体もコミットに含める。`.gitignore`には加えない（ブランチ上のコミット履歴として残すため）。squash mergeにより、mainには残らない。 |
| `docs/spec/機能名.md` | 人間＋AI | 永続（最新状態） | 背景・目的／仕様／影響範囲／設定項目／未決定事項・懸念点 | 「現在の正史」。実装完了のたびに最新仕様へ上書きする。新規作成時の人間承認は必須。 |
| `docs/adr/000N-タイトル.md` | 人間＋AI | 永続（不変） | 「〇〇を検討したが✕✕を採用した」という意思決定の背景・却下案 | 連番で管理し、一度マージしたら追記のみ（変更不可）。`docs/spec` の未決定事項が解消したら記録し、spec側の該当項目は削除してよい。些末な実装選択までは書かない。 |

`HANDOFF.md` は空でも各見出し（現在地／次回やること等）だけを残した状態でルート直下に存在させておき、使うときに埋める運用とする（都度新規作成はしない）。
