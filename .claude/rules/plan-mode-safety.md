# Planモードの安全な運用（Claude Code固有）

`ExitPlanMode` で計画をユーザーに提示する際に、**過去の計画テキストを誤って再送信する事故**が
実際に発生した（2026-08-15、issue #3 のセッション）。同種の事故を防ぐため以下を守る。

## 背景（何が起きたか）

同一セッション内で2つ目の計画を提示しようとした際、`plan` 引数に「既に承認・実行済みの
古い計画」の全文が入った状態で、3回連続して送信された。直前に対象ファイルをReadしてから
転記するという対策をとっても再発した。

原因は、同じ見出し構成（Context／実施内容／対象外／検証方法）の長文が会話履歴内に複数回
出現すると、出現回数の多い側（＝古い内容）へ生成が引っ張られること。`ExitPlanMode` は長文を
テキストとして丸ごと引数に渡す仕様であり、機械的なコピーではなく実質的な再生成になるため、
この混同が起きやすい。「気をつける」という意図レベルの対策では防げなかった。

## 守ること

1. **`plan` 引数は要約に留める**
   計画の全文を逐語転記しない。要点（目的／変更するファイル／やらないこと／検証方法）を
   数行〜十数行に要約して渡し、詳細は `plans/<名前>.md` 本体を正とする。長文の丸ごと再生成は、
   履歴内の類似テキストとの混同リスクを高めるため避ける。

2. **既存の承認済み計画の内容を失わない**
   同一セッション内で複数回計画を立てる場合も、既存の承認済み `plans/*.md` の内容を上書きして
   失ってはならない（`docs-workflow.md` の「plansはそのままコミットして履歴に残す」方針と同じ）。
   原則として計画ごとに新しいplanファイル名を使うことでこれを実現する。ただし規則6の制約
   （ハーネスがPlanモードre-entry時に同じファイルパスを提示し続ける）に対応する場合に限り、
   `.claude/scripts/src/archive-reentrant-plan.sh` で旧内容を確実に退避してから同じパスを再利用してよい
   （退避により内容は失われないため、この規則の趣旨には反しない。詳細は規則6）。

3. **送信直前のセルフチェック**
   `ExitPlanMode` を呼ぶ直前に、次の2点を確認してから送信する。
   - `planFilePath` が**今回のタスク用に作った**ファイルを指しているか
   - `plan` 引数の主題（タイトル・扱うファイル名）が、直前に自分が書いた計画と一致しているか

4. **異常を検知したら再試行せず止める**
   `ExitPlanMode` の返り値（Approved Planのエコー）が意図した内容と違っていた場合、同じ操作を
   繰り返さない。直ちに作業を止めてユーザーに状況を報告する。ツール経由での再現に失敗し続ける
   場合は、計画本文を通常のチャットメッセージとして直接提示し、ユーザーの明示的な確認を得てから
   実装に進む。

5. **承認の取り違えに注意**
   古い計画が「承認済み」の状態になっても、それを根拠に実装を進めてはいけない。ユーザーが
   承認したのは画面に表示された内容であって、こちらが意図した計画とは限らない。表示された内容と
   自分の意図がずれていると気づいた時点で、承認は無効として扱い、取り直す。

6. **同一セッション内でPlanモードへ複数回再突入する場合の対処**（issue #7対応のセッションで判明、
   issue #26でスクリプト化）
   `ExitPlanMode`は`plan`引数を取らず、ハーネスが「今回のplanファイル」として提示するパスから
   内容を読む仕様になっている（詳細は「背景」の事故発生時点とはツール仕様が異なる）。この方式は
   長文の丸ごと再生成という当初の事故原因自体は構造的に起きにくくするが、別の制約が判明した:
   **Planモードへ再突入するたびに、ハーネスは直前のre-entryで使ったplanファイルのパスを
   そのまま「今回のplanファイル」として提示し続ける**（新しいパスは割り当てられない）。
   規則2「既存の承認済み計画の内容を失わない」が定める例外（`archive-reentrant-plan.sh`での
   退避）は、この制約に対応するためのものである。以下の手順で対処する。

   旧手順（一時的にハーネス提示パスへ上書き→承認後に`git checkout`で復元）は、復元忘れや
   タイミングミスが起きると1回前の計画内容を破壊しかねず、かつ一時的な上書き内容がgit履歴に
   一切残らないという問題があった（issue #26）。代わりに、`.claude/scripts/src/archive-reentrant-plan.sh`
   を使い、ハーネス提示パスに残っている1つ前の計画を`_actN`付きの別名へ退避してから、
   ハーネス提示パスへ直接新しい計画を書く。

   - `EnterPlanMode`実行後、ハーネスが提示するplanファイルパスを確認する。
   - `bash .claude/scripts/src/archive-reentrant-plan.sh "<提示されたパス>"` を実行する（このセッション
     最初のre-entryではplanファイルがまだ存在しないためno-opになる。re-entry回数を問わず毎回
     実行してよい）。
   - 出力されたJSONの`archived`が`true`であれば、`planArchivedTo`（必要なら`worklogArchivedTo`）を
     確認し、直前の計画・worklogが失われず退避されたことを確かめる。
   - ハーネス提示パスへ**直接**新しい計画本文を書く。従来のような別名ファイルの作成や
     `git checkout`による復元は不要（このパス自体が今回の計画の正式なファイルになる）。
   - 退避されたファイル（`plans/<元の名前>_actN.md`、あれば`worklog/<元の名前>_actN.md`）は
     通常のcommit対象としてそのままgitへ追加してよい。1つ前の計画の履歴として残す。

   この手順では、ハーネス提示パスの**ファイル名自体**は結果的に前回と同じものを使い回すが、
   規則2に定める通り退避によって内容は失われないため、規則2に反しない。
