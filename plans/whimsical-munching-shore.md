# resume省略の再発防止（AIアセット改善）

## Context

新セッションで「レビューに新規コメントが付いたので対応してほしい」という依頼を受けた際、
`issue-mr-flow` の `resume` サブコマンド（`issue-mr-resume` サブエージェント経由の現在地確認）を
飛ばして、いきなり `comments` サブコマンドを実行してしまった。ユーザーからの指摘で発覚。

原因を確認すると、`resume` の発動条件が現在のSKILL.md／spec文書では
「issue番号やブランチ名を**知らない状態**で」という書き方になっている。しかしブランチ名は
`git branch --show-current` で常に機械的に取得できてしまうため、字義通り読むと「ブランチ名は
分かっている（＝knownの状態）」と判断でき、resumeを省略してよい理由に読めてしまう。
実際に今回はその読み方で飛ばしてしまった。

`resume` 本来の目的はブランチ名の特定ではなく、PR/MRの状態・未解決コメント件数・
plan/worklogファイル・HANDOFF.mdとの矛盾など「そのセッションでまだ確認していない現在地情報」を
集約することにある。つまり発動条件は「情報を知っているか」ではなく「**このセッションで現在地確認を
済ませたか**」で判定すべきであり、これは `.claude/rules/plan-mode-safety.md` で扱った過去のインシデント
（「気をつける」という意図レベルの対策では防げず、機械的に判定できる条件に直す必要があった）と
同じパターンの不備である。

## 実施内容

以下3ファイルの「resumeを使うべき条件」の記述を、「情報の有無」ベースから
「セッション内で現在地確認済みかどうか」ベースの機械的な条件に統一する。
ブランチ名やissue番号が判明していること自体はresume省略の理由にならない旨を明記する。

1. **`.claude/skills/issue-mr-flow/SKILL.md`**
   - 全体フロー表の直後にある誘導文（現行52-53行目付近）を、太字の断定形に強化し
     「`start` から始める場合を除き、このセッションで初めてこのフローのサブコマンドを使うときは
     必ず先に `resume` を実行する。`git branch --show-current` 等でブランチ名/issue番号が
     判明していることは省略してよい理由にならない」という趣旨に書き換える
     （`## レビュー完了合図の確認` 節と同じ、機械的チェックを促す文体に合わせる）。
   - `resume` サブコマンド節の冒頭説明（現行125-126行目）を同じ条件表現に揃える。
   - `sync` サブコマンド節（現行121行目）の「issue番号やブランチ名が分かっている場合に使う」を、
     「resume/startで現在地確認済みのセッション内でブランチを最新化したいだけの場合に使う。
     新しいセッションの最初の一手としては使わない」に修正し、同じ抜け道を塞ぐ。

2. **`dev-tools/docs/spec/issue-mr-workflow.md`**
   - 「途中引き継ぎ対応（resume）」節冒頭（現行109-111行目）の
     「`start` / `sync` はどちらも『issue番号やブランチ名を知っている』ことが前提」という記述を、
     上記と同じ「セッション内で現在地確認済みかどうか」ベースの説明に揃える
     （SKILL.mdは本spec文書の実装という位置付けのため、条件の定義がずれないようにする）。

3. **`.claude/agents/issue-mr-resume.md`**
   - frontmatterの `description` にある「issue番号やブランチ名を知らない状態（…）で」の一文を、
     1・2と同じ条件表現に揃える（他エージェント選定時の説明文としての整合性のため）。

いずれもテキストの言い回し修正であり、`Provider.ps1` 等の実処理コード・サブコマンドの手順番号・
全体フロー21ステップの構成には手を入れない。

## 対象外

- `dev-tools/src/vcs/*.ps1` 内の「知っている」等の無関係な既存コメント・文言（grep でヒットしたが
  resumeの発動条件とは無関係）。
- `plans/*.md` `worklog/*.md` の過去ファイル（スナップショットとして不変。書き換えない）。
- resumeサブエージェントの調査ロジック自体（手順1〜8）の変更。今回は「呼ぶかどうかの判定条件」の
  みが対象。

## 検証方法

- 3ファイルの該当箇所をdiffで確認し、「ブランチ名/issue番号の既知・未知」を条件にした表現が
  残っていないことを確認する（`知らない状態` `分かっている場合` 等の文言で再grep）。
- 修正後の文面を読み直し、「新セッションでいきなり `comments` や `reply` を使おうとした場合に、
  先に `resume` を呼ぶべきだと機械的に判断できるか」を自己チェックする。
- HANDOFF.mdの「現在地」に今回の対応を追記する（このタスク自体、全体フロー17
  AIアセット改善の一環として現在のissue #3ブランチ上で行う。新規issueは起票しない）。
- worklogファイル（`worklog/20260815_whimsical-munching-shore.md`）を作成し、原因と対応を記録する。
