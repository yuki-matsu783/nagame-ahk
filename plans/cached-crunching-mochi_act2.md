# 調査結果canvas形式HTML生成スキルを作る（issue #58）

## Context

issue #48（調査結果HTMLのTailwindCSS CDN方式確立）に関する対話の中で、通常の一覧・表形式では
表現しづらい「複数要素間の関連・依存関係」を主題とする調査結果向けに、codecanvas.app的な
ノード・エッジのcanvas形式（パン・ズーム・ノードホバーでの関連ハイライトに対応）が有効である
ことを、比較試作（TailwindCSS CDN通常版・自前ミニマムCSSハイブリッド版・リッチ演出版・canvas版の
4種、いずれもセッションスクラッチパッド上に作成・未コミット）を通じて確認した。issue #48は
「調査結果のHTML化のみ」に対象を限定していたため、この気づきはissue #58として別途起票し、
`issue-mr-flow`に沿って新ブランチ（`feature-58-canvas-format-report-skill`、Draft PR #59）で
進めることをユーザーと合意した。

issue化にあたり、ユーザーから「ノード・エッジの表現できる幅はリッチにしてほしい」との追加要望が
あり、単純な丸・直線を超えた表現力（ノード種別ごとの色・アイコン・形状、エッジのスタイル・方向・
ラベル・グルーピング等）が求められている。これを踏まえ、issue #58の受け入れ条件にも明記済み。

## 調査

### 調査の目的

上記の確定方針（TailwindCSS CDN + canvas形式のノード・エッジテンプレート、リッチな表現軸）を、
実際にスキルとして落とし込むための具体的な設計（判断基準の文言、テンプレートのノード/エッジ表現の
幅、他ドキュメントへの参照箇所）を確定し、次段階（作業計画）で迷いなく実装に着手できる状態にする。

### 調査項目

1. `.claude/skills/`配下の既存スキル（`commit`, `issue-create`, `ahk-implement`）のSKILL.md構成・
   frontmatterを確認し、新スキルの構成（判断基準の書き方、テンプレートファイルの配置場所）を
   どう合わせるか検討する。
2. セッション中に試作した4種のサンプル（scratchpad上、Tailwind通常/ハイブリッド/リッチ演出/
   canvas版）を再点検し、canvas版をベースにテンプレート化する際、どの部分を「固定の型」とし、
   どの部分を「ノード/エッジデータを差し替えるだけで使える変数部分」にするかを整理する。
3. 「ノード・エッジの表現の幅をリッチにする」要望を満たすため、以下の表現軸を追加設計する。
   - ノード: 種別ごとの色分けに加えて、アイコン（絵文字 or インラインSVG）・形状（角丸四角/丸/
     六角形等）・サイズ（重要度に応じた大小）
   - エッジ: 実線/点線、太さ、矢印の有無・方向（単方向/双方向）、ラベル、関係種類ごとの色分け
   - グルーピング: 関連ノードをまとめる「クラスタ枠」表現（例: 同じフォルダ配下のファイル群を
     1つの背景枠で囲む）
   これらをどこまでテンプレートの標準機能として持たせるか（凡例込みで）を設計する。
4. `.claude/skills/issue-mr-flow/SKILL.md`のflow-id 10の該当行に、新スキルへの参照をどう追記
   するか、既存の文体に合わせて文言案を作る。
5. `reports/<plan名>.html`の運用（`docs-workflow.md`のライフサイクル・`.gitignore`対象外等）は
   issue #48で既に確定済みのため、新スキルのテンプレートもこの運用にそのまま従えるか確認する。
6. `.claude/rules/markdown-frontmatter.md`の対象外ファイル表で、新スキルの`SKILL.md`が
   `.claude/skills/*/SKILL.md`として既に包含されているか確認する。
7. テンプレートの動作確認方法（ブラウザでの目視確認）について、issue #48のworklogに確認手順の
   前例があるか確認する（無ければ、今回はブラウザで開いて確認する旨を作業計画に明記する）。

### 調査対象外

- issue #48自体の内容・成果物（既に別issueとして完了済み。参照のみ行い変更しない）。
- skill-creatorが提示する本格的な評価ループ（with-skill/baselineのサブエージェント並列実行・
  ブラウザeval viewerでの比較）は行わない。「軽めのvibe check」の方針に基づき、作業計画実施後に
  テストプロンプトを自分で1〜2件実行し、生成結果を人間に見せて確認する形にとどめる
  （issue化の際にユーザー確認済み）。
- canvas形式以外の新たな表現形式（3D表示、外部グラフ描画ライブラリ（D3.js等）の導入）は検討
  しない。既存方針どおりTailwindCSS CDN + 素のJS/SVGの範囲に留める。

## 調査結果

### 1. 既存スキルの構成

`commit` / `issue-create` / `ahk-implement` の3スキルはいずれも `SKILL.md` 単体＋
`index.jsonl`（`.claude/scripts/src/extract-frontmatter.sh` が生成するfrontmatter索引。
人間が手動実行する運用で、AIが個別に編集するものではない）のみで構成されており、
`scripts/` `references/` `assets/` のようなサブディレクトリを持つ前例はリポジトリ内に無い。

→ 今回は新スキルにテンプレートHTMLというバンドルリソースが必須（判断基準の文章だけでは
「canvas形式のHTMLを生成する」を実現できない）ため、`skill-creator`の標準構成に倣い
`.claude/skills/<name>/templates/` にテンプレートファイルを配置する方針とする。既存3スキルとの
構成差は「バンドルリソースの要否」という妥当な理由によるものであり、問題ない。スキル名は
`canvas-report`（`/canvas-report`として呼び出せる）を提案する。

### 2〜3. プロトタイプの再点検とリッチな表現軸の設計

このセッションで試作した4種（Tailwind通常版・自前ミニマムCSSハイブリッド版・リッチ演出版・
canvas版）のうち、canvas版（ノード・エッジ形式）が「複数要素の関連を見せる」調査結果に最も
適していることを確認済み（issue #48の対話で合意済み、本issueのContext参照）。

今回、この判断を追加検証するため、**nagame-ahkの実コード（`src/features/`・`src/lib/`の
実際の`#Include`・関数呼び出し関係をgrepで抽出した実データ）を使い、リッチ化した表現軸を
組み込んだデモを`reports/cached-crunching-mochi.html`として試作した**（14ノード・21エッジ）。
実装・目視確認の結果、以下の表現軸がTailwindCSS CDN＋素のJS/SVGの範囲内（追加ライブラリ不要）で
問題なく実現できることを確認した。

- **ノードの形状**: `clip-path: polygon(...)` で六角形（lib/系）と角丸四角（features/系）を
  Tailwindの`rounded-xl`と併用して描き分けられる。丸・ダイヤ等も同じ手法で拡張可能。
- **ノードのアイコン**: 絵文字（⚡/🧩）をラベル先頭に添えるだけで種別が一目で分かる。
  インラインSVGアイコンに置き換える拡張も同じマークアップ構造で可能（今回は絵文字で十分と判断）。
- **ノードのサイズ**: 被参照数（ハブ度）をJSで集計し、3段階のTailwindユーティリティ組み合わせ
  （幅・パディング・フォントサイズ）に振り分けるだけで「重要なノードほど大きい」を表現できる。
  実データでは`Logger.ahk`が9箇所から参照される最大のハブとして視覚的に際立った。
- **エッジのスタイル**: `stroke-dasharray`（実線/破線）・`stroke-width`（太さ）・`stroke`
  （色）をJS側の「関係カテゴリ→スタイル」マップで一括管理し、SVG pathの属性へ反映するだけで
  6種類の関係（ログ出力・JSON変換・ウィンドウ操作・IPC通信・ウィンドウ監視イベント・
  ファイル監視通知）を色・線種で描き分けられた。
- **グルーピング（クラスタ枠）**: 同じグループに属するノードのx/y座標からJSで外接矩形を計算し、
  角丸破線の背景枠＋ラベルを1つ描画するだけで実現できた。今回は`src/features/`と`src/lib/`の
  2クラスタを表示し、「featuresはlibだけを経由し、features同士は直接依存しない」という
  `directory-structure.md`の設計ルールが、エッジがクラスタをまたいで`features→lib`方向にしか
  存在しないという形で視覚的にも裏付けられることを確認した（意図しない発見）。
- 双方向矢印（`marker-start`も設定する）は今回の実データでは該当する関係が無かったため未使用だが、
  `<marker>`要素をもう1つ定義し`marker-start`属性を足すだけで対応できる見込み（構造的な制約はない）。

これらはいずれも「ノード/エッジのデータ配列（`NODES`/`EDGES`）とスタイルのマッピング表
（`GROUP_STYLE`/`EDGE_STYLE`）を書き換えるだけで、HTML構造・パン/ズーム/ホバーハイライトの
JSロジックには手を入れずに使い回せる」設計になっている。→ 作業計画でテンプレート化する際は、
この`reports/cached-crunching-mochi.html`をベースに、`NODES`/`EDGES`/`GROUP_STYLE`/`EDGE_STYLE`
部分をプレースホルダ化する方針とする。

### 8. 追加要望（ユーザーフィードバック）への対応: 参照ハイライト・ミニマップ・詳細表示

調査結果の初回記録後、ユーザーから以下3点の追加要望があり、`reports/cached-crunching-mochi.html`を
v2へ更新して実現可能性を検証した。

- **参照関係のハイライト**（選択したトークンがどこで使われているか線で可視化）:
  現状のノード単位のホバーハイライト（v1で実装済み）が、まさにこれに相当する。**新たな実装は
  不要**で、「ノードをどの粒度で定義するか」の運用ルールの問題に帰着する。ファイル単位で
  ノードを作れば「ファイル間の参照」、関数・変数単位でノードを作れば「トークン単位の参照」を
  同じ仕組みでハイライトできる。→ スキルの判断基準に、「ノードの粒度は調査結果の主題に合わせて
  選ぶ（ファイル/モジュール単位が基本だが、関数・変数単位の参照関係を主題とする調査結果では
  その粒度でノードを定義してよい）」旨を明記する。
- **ミニマップ**: 全ノードを`WORLD_W`/`WORLD_H`に対する縮小座標で描画し、現在のビューポート範囲を
  矩形オーバーレイで示す小パネルを追加。クリック/ドラッグで該当座標へジャンプ（pan）できる。
  v2で実装・動作確認済み（右上に配置）。node数が増えても計算量は線形（O(ノード数)）で、
  パフォーマンス上の懸念は無い。
- **詳細表示でのmarkdown/mermaid表示**: ユーザーとの確認の結果、以下の方針で実装し、v2で動作確認済み。
  - markdown: **AI生成時にHTMLへ事前変換**する方針を採用（クライアント側の追加JSパーサ不要。
    これまでどおりTailwindCSS CDNのみで完結する）。
  - mermaid図: **mermaid.js をCDN経由で追加**する方針を採用（TailwindCSSに続く2つ目の外部CDN
    依存として許容。ユーザー確認済み）。ノードクリックで開く詳細パネル内に`<pre class="mermaid">`
    ブロックを動的挿入し、`mermaid.run({ nodes: [...] })`で描画する形で実装・動作確認した
    （`mermaid.initialize({ startOnLoad: false, ... })`とし、`startOnLoad`による自動走査ではなく
    パネルを開くタイミングで明示的に`run`する設計。動的に挿入した要素は自動走査の対象外のため）。
  - 「ズームアウトで全体像／ズームインで詳細」というcodecanvas.appの本来のコンセプト（連続的な
    セマンティックズーム）は、ノードの重なり・レイアウト崩れのリスクが高く実装コストも大きいため、
    **今回は「クリックで詳細パネルを開く」という単純化した操作に置き換えた**（結果として得られる
    「概要と詳細をシームレスに行き来できる」という体験は同等に満たせると判断）。この単純化の
    妥当性はユーザーへの提示・確認が必要な設計判断のため、作業計画提示時に明示する。

これらの追加要望により、テンプレートが持つべき機能（ノード/エッジのデータ差し替えに加え、
オプションで`detailHtml`/`mermaid`フィールド・ミニマップ・詳細パネルを持てること）が確定した。
