# 調査結果canvas形式HTML生成スキルを作る（issue #58）

## Context

issue #48（調査結果HTMLのTailwindCSS CDN方式確立）に関する対話の中で、通常の一覧・表形式では
表現しづらい「複数要素間の関連・依存関係」を主題とする調査結果向けに、codecanvas.app的な
ノード・エッジのcanvas形式（パン・ズーム・ノードホバーでの関連ハイライトに対応）が有効である
ことを、比較試作（TailwindCSS CDN通常版・自前ミニマムCSSハイブリッド版・リッチ演出版・canvas版の
4種、いずれもセッションスクラッチパッド上に作成・未コミット）を通じて確認した。issue #48は
「調査結果のHTML化のみ」に対象を限定していたため、この気づきはissue #58として別途起票し、
`issue-mr-flow`に沿って新ブランチ（`feature-58-canvas-format-report-skill`、Draft PR #59）で
進めることをユーザーと合意した。

issue化にあたり、ユーザーから「ノード・エッジの表現できる幅はリッチにしてほしい」との追加要望が
あり、単純な丸・直線を超えた表現力（ノード種別ごとの色・アイコン・形状、エッジのスタイル・方向・
ラベル・グルーピング等）が求められている。これを踏まえ、issue #58の受け入れ条件にも明記済み。

## 調査

### 調査の目的

上記の確定方針（TailwindCSS CDN + canvas形式のノード・エッジテンプレート、リッチな表現軸）を、
実際にスキルとして落とし込むための具体的な設計（判断基準の文言、テンプレートのノード/エッジ表現の
幅、他ドキュメントへの参照箇所）を確定し、次段階（作業計画）で迷いなく実装に着手できる状態にする。

### 調査項目

1. `.claude/skills/`配下の既存スキル（`commit`, `issue-create`, `ahk-implement`）のSKILL.md構成・
   frontmatterを確認し、新スキルの構成（判断基準の書き方、テンプレートファイルの配置場所）を
   どう合わせるか検討する。
2. セッション中に試作した4種のサンプル（scratchpad上、Tailwind通常/ハイブリッド/リッチ演出/
   canvas版）を再点検し、canvas版をベースにテンプレート化する際、どの部分を「固定の型」とし、
   どの部分を「ノード/エッジデータを差し替えるだけで使える変数部分」にするかを整理する。
3. 「ノード・エッジの表現の幅をリッチにする」要望を満たすため、以下の表現軸を追加設計する。
   - ノード: 種別ごとの色分けに加えて、アイコン（絵文字 or インラインSVG）・形状（角丸四角/丸/
     六角形等）・サイズ（重要度に応じた大小）
   - エッジ: 実線/点線、太さ、矢印の有無・方向（単方向/双方向）、ラベル、関係種類ごとの色分け
   - グルーピング: 関連ノードをまとめる「クラスタ枠」表現（例: 同じフォルダ配下のファイル群を
     1つの背景枠で囲む）
   これらをどこまでテンプレートの標準機能として持たせるか（凡例込みで）を設計する。
4. `.claude/skills/issue-mr-flow/SKILL.md`のflow-id 10の該当行に、新スキルへの参照をどう追記
   するか、既存の文体に合わせて文言案を作る。
5. `reports/<plan名>.html`の運用（`docs-workflow.md`のライフサイクル・`.gitignore`対象外等）は
   issue #48で既に確定済みのため、新スキルのテンプレートもこの運用にそのまま従えるか確認する。
6. `.claude/rules/markdown-frontmatter.md`の対象外ファイル表で、新スキルの`SKILL.md`が
   `.claude/skills/*/SKILL.md`として既に包含されているか確認する。
7. テンプレートの動作確認方法（ブラウザでの目視確認）について、issue #48のworklogに確認手順の
   前例があるか確認する（無ければ、今回はブラウザで開いて確認する旨を作業計画に明記する）。

### 調査対象外

- issue #48自体の内容・成果物（既に別issueとして完了済み。参照のみ行い変更しない）。
- skill-creatorが提示する本格的な評価ループ（with-skill/baselineのサブエージェント並列実行・
  ブラウザeval viewerでの比較）は行わない。「軽めのvibe check」の方針に基づき、作業計画実施後に
  テストプロンプトを自分で1〜2件実行し、生成結果を人間に見せて確認する形にとどめる
  （issue化の際にユーザー確認済み）。
- canvas形式以外の新たな表現形式（3D表示、外部グラフ描画ライブラリ（D3.js等）の導入）は検討
  しない。既存方針どおりTailwindCSS CDN + 素のJS/SVGの範囲に留める。

### 調査方法

- 1、4、6はそれぞれ該当ファイル（`.claude/skills/commit/SKILL.md`等、`issue-mr-flow/SKILL.md`、
  `markdown-frontmatter.md`）をReadし、既存の記法・構成を確認したうえで具体案をまとめる。
- 2、3はこのセッションで既に作成したscratchpad上のサンプル（canvas版プロトタイプ）をベースに、
  追加すべき表現軸を整理する（実際のテンプレートファイル執筆は作業計画・実装フェーズで行う）。
- 5、7は`docs-workflow.md`・issue #48のworklog（あれば）を確認する。

## 検証方法

本issueはスキル・テンプレートドキュメントの追加が中心のため、コード実行によるテストは無い。
以下で検証する。

- 完成した`.claude/skills/<name>/SKILL.md`とテンプレートを使い、実際のサンプルデータ（例:
  nagame-ahkの`features/`間の依存関係、または本issue自体の関連ドキュメント構造）でcanvas形式
  HTMLを生成し、ブラウザで開いてズーム・パン・ホバーハイライト・追加した表現軸（アイコン・
  エッジスタイル・グルーピング等）が意図通り動作するか目視確認する。
- `.claude/skills/issue-mr-flow/SKILL.md`のflow-id 10の追記が、既存の文体・表構成と整合して
  いるか通読して確認する。
