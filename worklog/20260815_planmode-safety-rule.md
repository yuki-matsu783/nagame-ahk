# worklog: planmode-safety-rule

対応するplan: `plans/planmode-safety-rule.md`
位置づけ: 全体フロー17（AIアセット改善）。issue #3 のセッション中に発生した事故を受けた再発防止。

## 何が起きたか

同一セッション内で2つ目の計画（`plans/pr4-review-followup2.md`）を `ExitPlanMode` で提示しようと
した際、`plan` 引数に**1つ目の計画（`plans/toasty-orbiting-finch.md`、既に承認・実行・commit済み）の
全文**が入った状態で送信された。これが3回連続で再発した。

- 1回目: 誤りに気づき、プランモードに戻って再提出 → 同じ古い内容が再送信された。
- 2回目: 同上。
- 3回目（ユーザーによる原因分析の指示後）: 「直前に対象ファイルをReadしてそのまま転記する」という
  対策をとったうえで再提出したが、やはり同じ古い内容が送信された。
- 4回目の試行では `ExitPlanMode` が「You are not in plan mode」エラーを返した。

実害（誤ったファイル書き込み・コマンド実行）は発生していない。誤承認のたびに即座にプランモードへ
戻ったため、`git status` は各時点で clean を維持していた。

## なぜなぜ分析（ユーザー指示により実施）

1. なぜ古い内容を提出したか → `plan` 引数のテキストが、新しく読んだファイルではなく古い計画と一致した。
2. なぜそちらと一致したか → 古い計画のテキストは会話履歴中に複数回出現していた（Write時・1回目の
   ExitPlanMode時・Approved Planのエコー）のに対し、新しい計画は2回しか出現していなかった。
   長文をパラメータとして再生成する際、出現頻度の高いテキストに引っ張られた。
3. なぜ意図が勝てなかったか → `ExitPlanMode` は長文をテキスト引数として渡す仕様であり、
   機械的なコピーではなく実質的な再生成になるため。加えて `EnterPlanMode` のシステムリマインダーが
   毎回「既存の計画ファイルは toasty-orbiting-finch.md」と古いパスを提示し続けたことも、
   パス選択を古い方へ引っ張る一因になった。
4. なぜ機械的な転記をしなかったか → 提出前に内容を突き合わせる仕組みを用意していなかった。
5. なぜ気づいた後も再発したか → 「気をつける」という意図レベルの対処のみで、やり方（生成方法）
   自体を変えなかったため。同じ手順を繰り返せば同じ失敗モードが再発する。

## 対応

`.claude/rules/plan-mode-safety.md` を新規作成し、`CLAUDE.md` の「Claude Code固有ルール」から
`@./.claude/rules/plan-mode-safety.md` でインポートする形にした。ルールの骨子:

1. `plan` 引数は全文の逐語転記ではなく要約に留める（詳細はplanファイル本体を正とする）。
2. 同一セッション内で複数回計画を立てる場合も、計画ごとに新しいplanファイル名を使う。
3. 送信直前に `planFilePath` と `plan` 引数の主題が今回のタスクのものか確認する。
4. 返り値のエコーが意図と違ったら再試行せず止め、ユーザーに報告する。ツール経由での再現に
   失敗し続ける場合はチャット本文で直接計画を提示して確認を得る。
5. 古い計画が承認済み状態になっても、それを根拠に実装を進めない（承認は無効として取り直す）。

## 検証

実際に4項目を適用して回避できた: 3回目の失敗後、`ExitPlanMode` の使用をやめ、計画本文を通常の
チャットメッセージとして直接提示 → ユーザーの「OK」を得て実装に進む、という流れで
`plans/pr4-review-followup2.md` の内容を正しく実行できた（commit 3c75b50）。
本ルール自体の提示も同じ方法で行い、正しく承認を得られた。
