# worklog: resume省略の再発防止（AIアセット改善）

plan: `plans/whimsical-munching-shore.md`

## 何が起きたか

新セッションで「新たにレビューに対してコメントしたので対応してほしい」という依頼を受け、
`issue-mr-flow` スキルをロードした後、`resume`（`issue-mr-resume` サブエージェント経由の現在地確認）
を飛ばして、いきなり `git branch --show-current` → `Get-MrForBranch` → `Get-MrUnresolvedComments`
という `comments` サブコマンド相当の手順を直接実行してしまった。

ユーザーから「ルール上、今フローのどこまで開発が進んでいるかをサブエージェントで判断する
ことになっていたはず」と指摘を受け、`issue-mr-resume` サブエージェントを起動しようとしたところ、
ユーザーがそのツール呼び出し自体を却下し、「resumeサブコマンドを利用できてなかったのを
再発防止してほしい。AIアセットを回収すること」という依頼に切り替わった。

## なぜなぜ分析

- なぜ`resume`を飛ばしたか: 「レビューコメント対応」というタスクの性質上、全体フロー9/15の
  `comments`/`reply` サブコマンドに直接該当すると判断し、そちらを優先してしまった。
- なぜそれで問題ないと判断したか: SKILL.mdの `resume` 発動条件が
  「issue番号やブランチ名を**知らない状態**で」という書き方だった。`git branch --show-current`
  は読み取り専用の機械的なコマンドで即座に実行でき、ブランチ名を得られたため、字義通り読むと
  「知っている状態」に該当し、resumeは不要と読めてしまった。
- 根本原因: `resume` 本来の目的は「ブランチ名の特定」ではなく、PR/MRの状態・未解決コメント件数・
  plan/worklogファイル・HANDOFF.mdとの矛盾など「このセッションでまだ確認していない現在地情報」の
  集約にある。しかし発動条件の文言が「情報の既知・未知」を基準にしていたため、目的とズレた
  ゆるい基準になっていた。
- 同種の過去事例: `.claude/rules/plan-mode-safety.md` に記録されている `ExitPlanMode` の計画
  とりちがえ事故も、「気をつける」という意図レベルの対策では防げず、機械的に判定できる条件へ
  直すことで対応した。今回も同じパターン（意図ベースの緩い条件→機械的な条件へ）で対応する。

## 対応

「情報の既知・未知」ではなく「**このセッションで現在地確認（resume/start）を済ませたか**」という
セッション単位の機械的な条件に発動条件を書き換えた。対象ファイルとその実施内容は
`plans/whimsical-munching-shore.md` の「実施内容」を参照。

- `.claude/skills/issue-mr-flow/SKILL.md`: 全体フロー表直後の誘導文、`resume`節冒頭、`sync`節の
  3箇所を修正。
- `dev-tools/docs/spec/issue-mr-workflow.md`: 「途中引き継ぎ対応（resume）」節冒頭を同条件に揃えた。
- `.claude/agents/issue-mr-resume.md`: frontmatterの`description`を同条件に揃えた。

## 検証結果

- `知らない状態` `分かっている場合` の文言が対象3ファイルから消え、
  「セッション内で現在地確認済みかどうか」ベースの表現に統一されたことをgrepで確認した。
